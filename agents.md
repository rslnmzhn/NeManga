# 🤖 Инструкции для AI-агентов (AGENTS.md)

Документ регламентирует стандарты разработки, правила тестирования и обязательства автономных агентов при работе с проектом **NeManga**.

---

## 🚨 Главное правило: обязательный мониторинг сборки (CI/CD)

> **Агент ОБЯЗАН следить за статусом сборки в GitHub Actions до полного завершения (Status: Success).**
> **Запрещено закрывать задачу сразу после выполнения `git push`, не убедившись, что релиз успешно собрался и опубликован.**

### Алгоритм действий агента при пуше изменений:
1. **Предварительная локальная проверка:**
   - Выполнить `flutter analyze --no-pub` — **строго 0 ошибок и предупреждений**.
   - Выполнить `flutter test --no-pub` — **все тесты обязаны проходить успешно**.
2. **Отправка коммита:**
   - Сформировать информативное сообщение коммита по соглашению Conventional Commits (`feat: ...`, `fix: ...`).
   - Отправить коммит в ветку `main` (`git push origin main`).
3. **Отслеживание сборки:**
   - Агент обязан проконтролировать процесс сборки на стороне GitHub Actions (через API/curl, git remote tags или проверку логов шагов `quality`, `resolve_release`, `build_android_release`, `publish_release`).
   - Если какой-либо шаг упал (exit code != 0):
     1. Немедленно локализовать причину падения (логи анализатора, упавший тест, ошибка сборки APK или загрузки артефактов);
     2. Внести исправление;
     3. Запустить локальные проверки;
     4. Отправить фикс-коммит и дождаться успешного завершения всего пайплайна (публикации релиза с APK).

## 🛠️ Правила написания тестов и кода

1. **Никаких локальных абсолютных путей:**
   - **Категорически запрещено** прописывать локальные абсолютные пути среды разработчика (например, `/home/burmalda/...`) в тестах, моках или исходном коде.
   - В CI GitHub Actions проект запускается в `/home/runner/work/...`. Любой захардкоженный локальный путь неизбежно уронит сборку в облаке.
   - Используйте относительные пути проекта (`assets/...`), `Directory.systemTemp` или синтетические байтовые моки.
2. **Подписи и keystore Android:**
   - И релизный, и отладочный типы сборки (`release` и `debug` в `android/app/build.gradle.kts`) должны использовать единую подпись `nemanga-release.jks`, чтобы избежать конфликтов `INSTALL_FAILED_UPDATE_INCOMPATIBLE` при автообновлении.
3. **Хранилище и Scoped Storage Android:**
   - Все файлы пользователя и архивы манги должны сохраняться в видимый системный каталог `Download/NeManga`.
   - При удалении исходников после сжатия агент обязан гарантировать удаление как временных файлов `cache/file_picker`, так и физических файлов в каталоге `Downloads` с вызовом `MediaScannerConnection`.
4. **Синхронизация версий приложения:**
   - При выпуске версий скрипт `apply_release_version.sh` обязан синхронизировать номер версии как в `pubspec.yaml`, так и в коде `UpdateService`.
   - Определение установленной версии в рантайме всегда должно считываться из `PackageManager` Android, чтобы исключить расхождения.
